CS-465 — Travlr Getaways — Full Stack Portfolio Journal
Full stack MEAN application for SNHU CS 465: a customer-facing site (Express/Handlebars) and an administrator single-page application (Angular) sharing one REST API and MongoDB database, secured with JWT-based login authentication.

Architecture
This project uses three distinct flavors of frontend development, each suited to a different job. The customer-facing site (app_server) is rendered with Express and Handlebars (HBS): a request hits a route, a controller fetches data and calls res.render(), and the server returns a complete HTML page the browser just displays — every interaction that needs new data (browsing a different page, viewing another trip) is a full page reload. Plain JavaScript supplements this layer for small client-side behaviors but isn't driving the page's structure or state. The admin side (travlr-admin) is an Angular single-page application: it loads once as a compiled TypeScript bundle and then runs almost entirely in the browser, with components (Login, TripListing, TripCard, TripEdit) talking to the backend through injectable services built on Angular's HttpClient, updating the DOM in place instead of requesting new pages. The tradeoff is complexity for capability — Handlebars is simple, requires no build step, and works even with JavaScript disabled, while Angular requires compilation and more client-side machinery but delivers instant UI updates, client-side routing, and the kind of stateful interactivity (login state, route guards, forms) a back-office admin tool needs.

The backend uses MongoDB, a NoSQL document database, because the application's data — trip packages and member accounts — maps naturally onto JSON-shaped documents rather than normalized relational tables. Mongoose schemas (travel.js, member.js) define that document shape directly in JavaScript, and because MongoDB documents and JSON are structurally the same thing, there's no translation layer between what's stored in the database, what the REST API returns, and what Angular or Handlebars consumes — the data keeps the same shape end to end. That flexibility also made it easier to evolve the schema as the project grew across modules without a formal migration process, and MongoDB Atlas provided a straightforward hosted option for a project with a small, evolving feature set.

Functionality
JSON and JavaScript are related but not the same thing: JSON (JavaScript Object Notation) is a plain-text data format — just structured strings, numbers, booleans, arrays, and objects, with no functions or logic of its own — while JavaScript is a full programming language that happens to read and write JSON easily (JSON.stringify() / JSON.parse()). JSON is what actually connects this project's three tiers: Mongoose documents from MongoDB get serialized into JSON by the Express API (res.json()), that JSON travels over HTTP to both the Handlebars-rendered customer site (via axios, feeding travel.js's controller) and the Angular admin SPA (via HttpClient, deserialized into typed objects like Trip and AuthResponse). Because every layer speaks JSON, the API genuinely doesn't care who's calling it — a browser, a server-side controller, or a Postman request all get the same shape of data back.

Several refactors improved functionality and efficiency along the way. The Module Five Separation of Concerns pass moved all direct MongoDB access out of app_server and into app_api, so the customer site now consumes the REST API exactly like any external client would, instead of touching the database directly — this meant a single source of truth for data access instead of two. In the trips controller, a shared toClientShape() helper replaced duplicated field-mapping code across the list, find, add, and update handlers, so the API's response shape only needs to be defined once. On the Angular side, extracting a reusable TripCard component out of TripListing meant trip markup and styling exist in exactly one place instead of being repeated for every card, and a single auth-interceptor now attaches the JWT to every outgoing request automatically rather than every service method doing it individually. The benefits of reusable components like this are consistency (one visual and behavioral source of truth), easier maintenance (a fix or style change applies everywhere at once), and better testability, since each component is small enough to have its own focused spec file.

Testing
A full stack application needs different testing strategies depending on the HTTP method involved. GET requests are the simplest to verify — read-only, idempotent, and safe to re-run — so testing them mostly means confirming the right data comes back with the right status code (200 for a found resource, 404 for one that doesn't exist). POST, PUT, and DELETE are mutating and need more care: POST isn't idempotent (sending it twice creates two resources), so tests need to account for that, while PUT and DELETE are idempotent but still need both a success case and failure cases (400 for bad input, 404 for a resource that no longer exists) explicitly tested. Adding JWT authentication multiplies this test surface. Before security existed, testing an endpoint was just "send a request, check the response." With a requireAuth middleware in place, every protected route now needs an extra setup step (obtaining a valid token first) just to reach the code under test, and the same endpoint now needs separate test cases for a missing token (401), an invalid or tampered token (401), and a valid token (the original success case) — proving the security actually works, not just that the feature works. I confirmed this directly testing the /api/trips write endpoints in Postman: the same POST request needed two different runs — no Authorization header expecting 401, then a valid Bearer token expecting 201 — to demonstrate both halves of the security protocol were functioning correctly.

Reflection
This course walked me through building a complete application the way it's actually done in industry — not a single layer, but a full chain from database schema to REST API to two different frontends, with the Separation of Concerns and MVC patterns tying it together intentionally rather than as an afterthought. The skills I leaned on most, and will carry forward, are REST API design (choosing resource-oriented routes, consistent status codes, and a clean JSON contract), NoSQL data modeling with Mongoose, building a real Angular SPA with components, services, reactive forms, routing, and dependency injection, and implementing authentication and security from scratch — password hashing, JWT issuance and verification, and protecting specific endpoints rather than the whole application. Beyond the code itself, debugging real build and runtime errors independently, testing an API deliberately with Postman instead of just clicking through the UI, and working with Git branches across modules all mirror how I'll actually work on a development team. Together these make me a considerably more marketable candidate for junior full-stack or backend developer roles, since MEAN-stack fundamentals, REST API design, and applied security are exactly what those postings ask for.
